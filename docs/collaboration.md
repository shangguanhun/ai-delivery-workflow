# 协作模式：职责清楚，交接尽量少

这是部署者可采用的方法，不是产品功能说明。这里的“网页版 Chat”指获授权的分析/作者会话，“Dot”指可选协调工具或协调会话，“本地”按实际执行环境判定。任何名称都不保证自带工具、权限、长期记忆或后台任务。

## 谁负责什么

| 职责 | 负责结果 | 不自动拥有的权利 |
| --- | --- | --- |
| 用户 | 目标、反馈、预算、授权、暂停/恢复及最终体验意见 | 无需充当首轮工程 QA |
| 网页版产品/规则作者 | 来源核验、产品取舍、完整任务包、规则候选；按授权作产品判断 | 不因写了计划就控制本地进程或获得发消息权限 |
| Dot 协调与核查 | 边界/脱敏核查、确切版本与收件人核对、原文交接、授权内发布/迁移 | 不替原作者补写定稿、不创造设计、模型或执行授权 |
| 执行主控 | 守住批准方向，处理依赖、写域、预算风险、技术采用及必要决策 | 不替代网页设计，不把每次检查揽为机械中转 |
| 主要实现者 | 完整里程碑的实现、自检、集成、修复、候选和用户入口 | 不自充独审、不擅改产品承诺或真实数据 |
| 独立审查者 | 对确切候选与风险给结论、反例 | 不代修、不采用自己审查的候选、不替用户 ACCEPT |

这是职责，不是必建六个角色。小任务可只有用户和一个 AI，真实高风险才需要独立审查。已有一位工程负责人兼主实现者且授权允许时，不为形式新增管理者；若既有主控与作者分工有效，保持它们。

## 一次典型循环

用户说清希望得到的结果和不想要的偏移。网页作者读授权材料，区分事实、用户体验反馈、假设与新建议，给出有界结果包。Dot 核查材料边界和版本后原文交接；工程主控在安全节点核本地现状，复用成果并安排一名主要实现者做到底。必要独审和实际操作可以按适用边界独立进行，反例直接回作者。完整候选从真实入口交给用户，反馈只改变实际需要改变的部分。

网页作者决定“做成什么、什么体验算成立”；本地主控决定“怎么接到当前实现、哪个顺序/工具合适”。工程建议可以反馈，但不能把“技术较方便”当成偷偷缩小产品目标的理由。网页也不把实现细枝末节逐项变成设计签收。

## 何时不用多代理

局部文案、小范围明确修复、单一数据整理等，往往没有独立并行收益，可以同一会话完成。复杂任务也不一定多代理：如果每步都要共享同一状态和诊断，交接可能比顺序执行更贵。必要审查的独立性是风险要求，不是鼓励多开几个模型。

值得并行的例子是稳定接口下的独立素材准备，或冻结候选的源码独审与互不争用的证据整理。共享 GUI、存档或同一文件的工作应串行。总负责人接回结果并验证整合，不把“已分配”当交付。

## 把大任务保持完整

一个完整可用里程碑可以含机制、界面、持久化和异常恢复；它的内部步骤不必各自可玩。先稳定共用机制，再用不同内容验证复用，不为了避风险把整体缩到一个特例，也不先铺大量内容掩盖机制失败。

检查点关注完整路径是否成立。普通修复留同一任务，合并同因和邻近风险；两轮仍无结果就选改变前提或方法，而非重复换标题。模型按整体耦合、能力、风险和总成本选择，需求明确不等于可以用不足能力。

## 暂停与退出不是同一件事

用户暂停阻止其范围内继续制作、派发或恢复。协调回合无事可做时可以安全结束，但仍保留接收责任与可用返回路径；这不是取消作者或放弃交付。任务中断原因未明先核现状，不能把 idle 解释成恢复许可。

规则升级或建新库都不解除旧暂停、失败或验收门。先完成授权的规则维护，等项目获准继续时再安全重载和接续。
