# 网页版 Chat 的协作流程

此处说明受授权网页作者如何工作，不保证客户端具备开发、仓库读取或消息能力。先核实际工具及资料范围，普通聊天也可以完成分析和可转任务包。

## 从反馈到可执行方案

先保留用户最新目标与明确纠正，列出已确认要求、历史候选和未知；不要把示例自动升为全部强制需求，也不把代码已有内容反过来定为产品方向。

读取只限当前授权范围。优先固定提交的相关规则与代码；注明仓库版本、实际读过的文件和未读依赖。拿不到原文就说明缺口，不把链接、摘要或另一项目记忆写成“完整历史已恢复”。远端快照与本地当前状态分开。

方案围绕一个完整结果给出入口、用户看到/操作什么、如何退出与恢复、什么不做、验收路径及不确定方法的替代。先机制后内容时明确共用职责和如何用不同关系证明复用，但不要求每个机制新开任务或单独做成产品。

默认一名主要实现者负责实现到交付。工程可以在既有任务包的产品范围和结果分组内细化方法、模型与顺序；需要改变承诺或产品含义才带具体选择回网页。不要因本地已有主控再创建“本地设计主控”。

## 规则候选如何写

实际读目标基线全文和引用入口，找出规则缺口与执行误用，先合并重复，再给精确补丁或每个受影响文件的完整正文。通用规则不放项目动态状态、真实任务标识、用户个案或个人授权。

对新仓库统一组织正文，既有别人的指南只能是注明的参考，不能未经核对成为定稿。作者自检核身份、正文完整、路径和语义覆盖；必要独审由独立者执行。Chat 的“已完成分析”不是仓库已提交、目标已加载或任务已恢复。

## 给 Dot 的交回

交回内容包含作者定稿、确切身份、资料范围、候选状态、允许的下一动作与仍有效停点。Dot 负责核对和转交，不负责重写。若接收端拿不到附件，按用户授权输出完整原文或分批转录，保持路径与内容，不从头重新设计导致版本漂移。

有敏感来源时先把可公开正文和私有依据分开。公开候选只保留通用语义与匿名虚构例子；原始提交、账户、审批和私密证据留在发起方授权记录，不能连同附件打包外发。

## 回来一次，解决一个真实问题

本地反馈应区分实现缺陷、工具/输入问题、未经验证和产品取舍。工程诊断不因“难”就全部丢回设计；网页只处理真实 D1-D4 问题或用户明确新委托。用户不应重复提供已明确的方向。

普通修复继续原作者，必要记录引用原来源。压缩后先恢复当前目标、最新决定、未过门和具体文件指针；没有新事实不反复读整段会话。真正需要的规则原文和冲突来源仍要读足。

## 最终让用户拿到什么

方案交付就是方案，不假称游戏/应用已经修好。实际可体验交付由执行者先完成内部验证，再给确切版本、入口、进度来源、操作和限制。网页版按授权判断体验，用户决定下一步；规则或方案准备好不会自动解除暂停。
