# 新仓库与安全迁移

本指南是后续授权采用步骤，不是建仓、push、通知或恢复指令。当前候选状态见 [STATE](../STATE.md)。在规则维护授权与项目恢复授权不同的情况下，二者分别处理。

## 1. 新库只接收净化后的工作树

核外部文件清单，只选择本候选的通用正文、模板和虚构示例。不要 fork、镜像或复制旧 `.git`，不导入旧分支、标签、提交历史、发布附件、审查记录或私密聊天。旧库原件与历史保持原处，不为净化新库重写或删除旧历史。

扫描正文、文件名、配置、链接、元数据及归档成员。原始账号、任务身份、绝对路径、私人版本指针、个人授权、实际个案、真实进度和凭证不得进入新库。必要来源核验留发起方授权记录；新库只保存 [通用映射](semantic-map.md)。哈希相同不代表已经脱敏。

## 2. 独审与私有创建

网页作者给确切候选，Dot 可核资料边界与字节。由符合阶段 3 的独立审查者审查规则/迁移风险；Dot 若是采用者，不能自充该独审。发现正文问题回原作者，不由协调者临场定稿。

在建仓/push授权有效后，获授权采用者建立空的私有仓库，核实际账号、远端和可见性，只暂存已核文件。不要使用 `git add .` 或带入旧历史。服务端默认、可见性和提交回读未确认前，不报告创建/上传成功；不得为解决工具缺口擅自购买或更改权限。

私有建仓仍是外部写入，不从“以后可能公开”推导授权。首次核验产生的新库身份、提交与接收证据留部署记录，不把个人身份补进公共模板。

## 3. 各项目独立采用，不搬入项目规则

原项目的专属规则、实际目录、模型选择、数据、当前任务、未提交内容及冻结证据继续在原项目。先在用户允许的安全节点核原有效规则链与适用覆盖，把公共入口指向新库的确切已采用提交。只做必要指针/冲突修复，不覆盖项目 AGENTS 或重建所有任务。

停点、失败、拒绝、旧档兼容、预算及独审门保留。候选里不再有个人默认，并不等于项目的明确模型选择失效；它应由原项目来源继续约束。没有运行授权时可以准备规则候选，但不启动项目验证以证明迁移。

旧加载路径全部保留，见语义映射。路径相同不意味着正文和权限完全相同，尤其备份/push不再有任何来自他人的常设授权。冲突只阻止依赖它的变更，不能通过“通用规则更简单”跳过既有停点。

## 4. 加载与通知分开

对允许继续的目标，在不打断有效回合的安全节点核加载版本与适用文件。未实际读取只标待加载；仓库可读、入口已改、任务已加载和实际模型路线分别判断。没有工具支持时返回具体缺口，不声称自动迁移。

只有明确授权通知时才向核实接收方发版本和范围说明。若消息会自动触发运行，且未获恢复许可，不直接发给暂停任务，保留给用户安排的通知稿。已有可靠通知足够，不加迁移监控或反复催回执。

## 5. 回退范围

采用前保存原公共指针、相关规则字节与现有任务状态入口。新规则读取或兼容有问题时，只回退本次获授权的规则/指针变更；不 reset 工程、不删进度、不撤销他人未提交代码。保留失败与迁移缺口，不能用回退追认通过。

## 6. 将来公开是另一项决定

公开前重新检查内容、所有新库历史、Issue/讨论、附件、Pages/发布资产和模板填写情况，范围只限用户授权的新库。核作者权利与明确许可证，删除私密内容须按合法授权处理，且不能仅删工作树就认为历史无泄漏。

默认保持私有。公开可见性、开源许可、允许第三方复用不是同一件事；当前包不代用户选择许可证，也不以一份候选自检宣称公开安全。完成对应审查与明确授权后，才执行并验证公开动作。

## 最小采用记录

沿原部署/项目记录保存：候选身份与独审、准许的外部动作、实际新库提交/可见性、目标入口变更、各目标加载与未迁移项、回退输入。没有新事实不重复记录，不在公共库写项目状态。
